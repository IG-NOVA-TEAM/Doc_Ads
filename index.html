Tổng quan

Ads Flow hoạt động như thế nào

Khi bạn khai báo dependency và cho MyApplication kế thừa AdsFlowApplication, thư viện tự lo toàn bộ luồng điều hướng. Màn hình LAUNCHER là SplashActivity của thư viện — app của bạn không cần khai báo.

Trường hợp 1 (isOnboardingOnce = false, Mặc định):
[SplashActivity] ➜ [LanguageStartActivity] ➜ [IntroActivity] ➜ [MainActivity của bạn]

Trường hợp 2 (isOnboardingOnce = true):
• Lần đầu mở: [SplashActivity] ➜ [LanguageStartActivity] ➜ [IntroActivity] ➜ [MainActivity]
• Từ lần 2 trở đi: [SplashActivity] ➜ [MainActivity] (bỏ qua Language & Intro)

↳ Khi ẩn app rồi mở lại: mở [WelcomeBackActivity] nếu cờ Ads Resume bật và màn hình không bị loại trừ

Quản lý trạng thái bằng SharedPreferences

Thư viện lưu trạng thái Onboarding và tùy chọn ngôn ngữ trong SharedPreferences (tên file ignova_ads_flow_pref):

Cờ trong SharedPreferencesÝ nghĩaHàm đọc/ghi
key_ads_onboarding_completed Đã hoàn thành toàn bộ Onboarding (qua Intro/NativeFull) AdsFlow.isOnboardingCompleted(ctx)
AdsFlow.setOnboardingCompleted(ctx, true)
key_ads_language_done Người dùng đã chọn ngôn ngữ ở LanguageStart AdsFlow.isLanguageDone(ctx)

key_ads_intro_done Người dùng đã xem xong slide onboarding AdsFlow.isIntroDone(ctx)

Nguyên lý điều hướng

  1. SplashActivity — luôn chạy đầu tiên Khởi tạo SDK, fetch Remote Config, tải cấu hình UI do app truyền qua AdsFlowConfig.
  2. Kiểm tra Onboarding qua AdsFlow.shouldShowOnboarding(context)
    • Nếu config.isOnboardingOnce == false: Luôn trả về true $\rightarrow$ Mở LanguageStartActivity, sau đó sang IntroActivity rồi mới về MainActivity.
    • Nếu config.isOnboardingOnce == true: Kiểm tra !isOnboardingCompleted(context). Nếu chưa xong Onboarding $\rightarrow$ mở LanguageStartActivity; nếu đã xong ở lần trước $\rightarrow$ đi thẳng MainActivity.
  3. Khi mất kết nối Internet Nếu không có mạng, SplashActivity tự động điều hướng sang NoInternetActivity.

Bước 1

Tích hợp Maven Artifact

Thư viện được publish dưới tên com.ignova:ads-flow-normal lên GitHub Packages. Bạn cần khai báo kho lưu trữ, thông tin xác thực và dependency.

1.1. Khai báo kho lưu trữ Maven

Trong settings.gradle.kts, thêm kho GitHub Packages vào dependencyResolutionManagement:

settings.gradle.kts gradle 
dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories {
        google()
        mavenCentral()

        // Kho chứa com.ignova:ads-flow-normal và com.ignova:ad-lib
        maven {
            name = "GitHubPackages"
            url = uri("https://maven.pkg.github.com/IG-NOVA-TEAM/INV_Lib_Ads_Default")
            credentials {
                username = providers.gradleProperty("gpr.user").orNull
                    ?: providers.environmentVariable("GH_USERNAME").orNull
                    ?: providers.environmentVariable("GITHUB_ACTOR").orNull
                password = providers.gradleProperty("gpr.key").orNull
                    ?: providers.environmentVariable("GH_PAT").orNull
                    ?: providers.environmentVariable("GITHUB_TOKEN").orNull
            }
        }
    }
}

1.2. Khai báo thông tin xác thực

Kho yêu cầu xác thực. Đặt thông tin vào gradle.properties ở thư mục gốc project, hoặc an toàn hơn là đặt ở ~/.gradle/gradle.properties trên máy cá nhân để không bị commit lên Git.

gpr.key=YOUR_GITHUB_PAT

PAT cần quyền read:packages. Không commit giá trị thật vào gradle.properties trong repo. Nếu gặp lỗi 401, xem mục 12.1.

1.4. Khai báo ID ứng dụng (AdMob & Facebook)

Thư viện khai báo sẵn trong manifest các meta-data cần giá trị ứng dụng của bạn. Vì vậy bạn bắt buộc phải cấp 3 giá trị này qua manifestPlaceholders trong defaultConfig — nếu thiếu, build sẽ fail với lỗi "requires a placeholder substitution but no value for … is provided".

app/build.gradle.kts gradle 
android {
    defaultConfig {
        applicationId = "com.example.myapp"
        minSdk = 24
        targetSdk = 37

        // Bắt buộc — AdMob App ID (lấy trong AdMob Console)
        manifestPlaceholders["admobAppId"] = "ca-app-pub-xxxxxxxxxxxxxxxx~yyyyyyyyyy"

        // Bắt buộc — Facebook App ID
        manifestPlaceholders["facebookAppId"] = "1234567890123456"

        // Bắt buộc — Facebook Client Token
        manifestPlaceholders["facebookClientToken"] = "abcdef0123456789abcdef0123456789"
    }
}
Giải thích từng placeholder
Placeholder
Ý nghĩa & cách lấy
admobAppId

AdMob App ID — định danh ứng dụng trong hệ thống Google Ads.

Lấy ở AdMob Console → App Settings → App ID. Định dạng: ca-app-pub-xxxxxxxxxxxxxxxx~yyyyyyyyyy — có dấu ~ ở giữa.

Quan trọng: đây là App ID (dấu ~), không phải Ad Unit ID (dấu /) mà bạn khai báo ở Remote Config.

Test ads của Google dùng App ID: ca-app-pub-3940256099942544~3347511713 — dùng ID này khi phát triển.

facebookAppId

Facebook App ID — dùng cho Facebook Audience Network (một nguồn quảng cáo trong mediation).

Lấy ở Meta for Developers → My Apps → Settings → Basic — trường App ID.

Đây là chuỗi số, ví dụ 1234567890123456. Nếu app không dùng Facebook, vẫn phải đặt một giá trị (chuỗi rỗng cũng được) vì thư viện khai báo sẵn meta-data này.

facebookClientToken

Facebook Client Token — dùng để gọi Facebook Graph API (ví dụ lấy access token cho ads).

Lấy ở Meta for Developers → My Apps → Settings → Basic → Client Token, hoặc tự sinh trong Settings → Advanced → Client Token → Generate.

Đây là chuỗi hex 32 ký tự, ví dụ abcdef0123456789abcdef0123456789.

🐛 Lỗi dễ gặp: dính ký tự thừa trong App ID

AdMob App ID phải kết thúc bằng 9 chữ số sau dấu ~. Nếu bạn copy-paste nhầm và bị dính thêm ký tự, ví dụ:

ca-app-pub-3940256099942544~3347511713m ← sai, có chữ "m" thừa

ca-app-pub-3940256099942544~3347511713 ← đúng

App vẫn build được và vẫn chạy, nhưng quảng cáo không bao giờ hiện — Google Ads từ chối App ID không hợp lệ và chỉ ghi log lỗi, không báo trong UI.

Cách kiểm tra: sau khi build, mở app/build/intermediates/merged_manifest/<buildType>/…/AndroidManifest.xml, tìm dòng com.google.android.gms.ads.APPLICATION_ID và đối chiếu kỹ với giá trị trong AdMob Console.

⚠️ Ba giá trị này không được để trống khi phát hành

Giá trị test của Google (ca-app-pub-3940256099942544~3347511713) chỉ dùng khi phát triển. Nếu bạn phát hành app với App ID test, AdMob sẽ không hiển thị quảng cáo thật và tài khoản AdMob của bạn có thể bị gắn cờ.

Cách an toàn nhất là để ID nằm trong biến môi trường thay vì hard-code, rồi đổi giá trị theo build type:

app/build.gradle.kts — tách ID theo build type 
android {
    defaultConfig {
        manifestPlaceholders["facebookAppId"] = ""
        manifestPlaceholders["facebookClientToken"] = ""
    }

    buildTypes {
        debug {
            manifestPlaceholders["admobAppId"] =
                "ca-app-pub-3940256099942544~3347511713"  // test ads
        }
        release {
            manifestPlaceholders["admobAppId"] =
                providers.gradleProperty("admobAppId").get()      // ID thật
        }
    }
}

📌 Tự kiểm tra trước khi phát hành

Mở app/build/intermediates/merged_manifest/<buildType>/…/AndroidManifest.xml sau khi build và tìm dòng com.google.android.gms.ads.APPLICATION_ID — giá trị phải là App ID của bạn, không phải ID test.

📌 Bắt buộc

Thư viện dùng ViewBinding và Java 17. Nếu project của bạn chưa bật ViewBinding, hãy bật ở module app:

app/build.gradle.kts

    viewBinding = true
}

Bước 2

Cấu hình AndroidManifest.xml

Thư viện tự khai báo sẵn toàn bộ màn hình flow (SplashActivity, LanguageStartActivity, IntroActivity, WelcomeBackActivity, NoInternetActivity, NativeFullActivity) cùng các quyền mạng và meta-data AdMob. App của bạn chỉ cần khai báo Application class và trỏ màn hình LAUNCHER về SplashActivity của thư viện.

2.1. Manifest đầy đủ

app/src/main/AndroidManifest.xml xml 
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools">

    <application
        android:name=".MyApplication"
        android:allowBackup="true"
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:roundIcon="@mipmap/ic_launcher_round"
        android:supportsRtl="true"
        android:theme="@style/Theme.MyApp"
        tools:ignore="DiscouragedApi,LockedOrientationActivity">

        <!-- Màn hình LAUNCHER: SplashActivity của thư viện -->
        <activity
            android:name="com.ignova.adsflow.flow.splash.SplashActivity"
            android:exported="true"
            android:screenOrientation="portrait"
            tools:replace="android:exported">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>

        <!-- Màn hình chính của app. KHÔNG thêm intent-filter -->
        <activity
            android:name=".MainActivity"
            android:exported="false"
            android:screenOrientation="portrait" />

    </application>
</manifest>

2.2. Vì sao phải trỏ LAUNCHER về SplashActivity?

SplashActivity của thư viện được khai báo android:exported="true" nhưng không kèm intent-filter MAIN/LAUNCHER — vì thư viện không biết app của bạn muốn dùng màn nào làm màn hình khởi động. Nhờ vậy bạn có thể tự do chọn:

Cách khai báoKết quảNên dùng khi
Trỏ LAUNCHER về SplashActivity của thư viện App mở ra → Splash của thư viện → ngôn ngữ → onboarding → Main của bạn Mặc định — muốn dùng flow onboarding của thư viện
Đặt LAUNCHER trên MainActivity của bạn App mở thẳng vào Main, bỏ qua flow App đã có flow riêng, chỉ muốn dùng phần quảng cáo

🐛 Dễ sai nhất: khai báo trùng LAUNCHER

Nếu bạn đặt intent-filter MAIN/LAUNCHER trên cả SplashActivity và MainActivity, hệ thống sẽ hiện hộp thoại "Open with" mỗi lần mở app. Chỉ một activity được mang LAUNCHER.

Nếu bạn đặt LAUNCHER trên MainActivity mà quên khai báo SplashActivity, ứng dụng vẫn chạy nhưng không có màn Splash của thư viện — các quảng cáo splash (native/inter/app-open) sẽ không bao giờ hiển thị.

📌 tools:replace="android:exported"

Thư viện khai báo SplashActivity với android:exported="true". Khi bạn khai báo lại activity này trong app manifest, manifest merger sẽ báo xung đột giá trị. Thêm tools:replace="android:exported" để chỉ định rõ giá trị của app thắng — như trong ví dụ ở mục 2.1.

2.4. Firebase (Remote Config & Analytics)

Thư viện dùng Firebase Remote Config làm nguồn cấu hình và Firebase Analytics để ghi event. Vì vậy app của bạn cần thêm:

  1. File google-services.json Đặt tại app/google-services.json (thư mục app/, không phải app/src/main/). File này chứa api_key, project_id, app_id — những giá trị Firebase cần để khởi tạo.
  2. Apply plugin google-services Trong app/build.gradle.kts:
app/build.gradle.kts 
plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.google.services)
}

dependencies {
    implementation(platform(libs.firebase.bom))
    implementation(libs.firebase.config)      // Remote Config
    implementation(libs.firebase.analytics)  // Analytics
}

✅ Firebase là tuỳ chọn, không bắt buộc

Nếu app chưa apply plugin google-services hoặc thiếu google-services.json, thư viện vẫn chạy bình thường: Remote Config trả về null và Analytics bỏ qua event, chỉ ghi log warning. Ads sẽ dùng cấu hình mặc định — app không bị crash.

Nhưng nếu bạn muốn bật/tắt quảng cáo từ server (mục 10) thì Firebase là bắt buộc.

3.2. Khai báo màn hình

Override configureFlow() và truyền activityMap. Đây là nơi duy nhất thư viện biết app của bạn ở đâu.

MyApplication.kt kotlin 
package com.example.myapp

import android.app.Activity
import com.ignova.adsflow.core.AdsFlowApplication
import com.ignova.adsflow.flow.AdsFlowConfig
import com.ignova.adsflow.flow.FlowTarget

class MyApplication : AdsFlowApplication() {

    override fun configureFlow(): AdsFlowConfig = AdsFlowConfig(
        activityMap = mapOf(
            // Bắt buộc — màn hình chính của app
            FlowTarget.MAIN to MainActivity::class.java,

            // Tuỳ chọn — dùng màn WelcomeBack riêng thay vì mặc định
            FlowTarget.WELCOME_BACK to MyWelcomeBackActivity::class.java,
        )
    )
}

⚠️ excludedFromWelcomeBack() — Chặn WelcomeBack mở nhầm

Mặc định thư viện đã tự động loại trừ 4 màn hình: SplashActivity, NativeFullActivity, NoInternetActivity, WelcomeBackActivity, đồng thời tự động bỏ qua các Activity nội bộ của AdMob (com.google.android.gms.ads.*). Nếu app của bạn muốn chặn WelcomeBack khi người dùng ẩn/mở lại app tại màn LanguageStartActivity, IntroActivity hoặc các màn riêng (như Paywall, Webview thanh toán), hãy override hàm này:

MyApplication.kt — thêm excludedFromWelcomeBack 
import com.ignova.adsflow.flow.language.LanguageStartActivity
import com.ignova.adsflow.flow.splash.SplashActivity
import com.ignova.adsflow.flow.splash.NativeFullActivity
import com.ignova.adsflow.flow.nointernet.NoInternetActivity
import com.ignova.adsflow.flow.welcomeback.WelcomeBackActivity

override fun excludedFromWelcomeBack(): Set<Class<out Activity>> = setOf(
    SplashActivity::class.java,
    LanguageStartActivity::class.java, // Thêm màn cần chặn vào đây
    NativeFullActivity::class.java,
    NoInternetActivity::class.java,
    WelcomeBackActivity::class.java
)

3.3. Bảng FlowTarget

Các key chuẩn mà thư viện dùng để điều hướng:

KeyHằng sốÝ nghĩa

flow_target_welcome_backFlowTarget.WELCOME_BACKMàn WelcomeBack khi app resume. Không map thì dùng mặc định của thư viện
flow_target_no_internetFlowTarget.NO_INTERNETMàn mất kết nối
flow_target_languageFlowTarget.LANGUAGEMàn chọn ngôn ngữ (nếu app tự làm)

Nếu bạn cần đích tuỳ chỉnh, dùng customTarget(name) để tránh trùng key chuẩn:

MyApplication.kt 
// → "app_custom_paywall"
val paywallKey = customTarget("paywall")

override fun configureFlow(): AdsFlowConfig = AdsFlowConfig(
    activityMap = mapOf(
        FlowTarget.MAIN to MainActivity::class.java,
        paywallKey to PaywallActivity::class.java
    ),
    isOnboardingOnce = false // true: chỉ đi onboarding lần đầu; false: luôn đi full mỗi lần mở app
)

📌 Shortcut có sẵn trên Application

AdsFlowApplication đã expose sẵn các shortcut, không cần import AdsFlow:

  • isOnboardingCompleted() / setOnboardingCompleted(true) — kiểm tra/đánh dấu hoàn tất onboarding
  • shouldShowOnboarding() — kiểm tra có cần đi qua onboarding không (dựa trên isOnboardingOnce)
  • isLanguageDone() / setLanguageDone(true)
  • isIntroDone() / setIntroDone(true)
  • isShowingAd — trạng thái có đang hiển thị quảng cáo nào không
  • isShowResume — cờ tổng bật/tắt WelcomeBack + App Open Resume
  • currentActivity — activity đang foreground
  • isAppForeground — app đang foreground hay background

📌 Quy ước đặt tên thuộc tính

Mỗi thuộc tính UI có hai biến thể: một biến nhận giá trị trực tiếp và một biến hậu tố Res nhận resource id. Thư viện luôn ưu tiên giá trị trực tiếp nếu có, ngược lại mới đọc từ resource.

Bước 8

Tắt quảng cáo (In-App Purchase)

Thư viện có sẵn cơ chế tắt quảng cáo ở tầng lõi. Override defaultAdSuppressor() và trả về true khi người dùng đã mua gói — mọi định dạng quảng cáo sẽ tự động bị bỏ qua, không cần thêm if ở từng màn hình và không phát sinh request mạng nào.

MyApplication.kt kotlin 
import android.app.Activity

class MyApplication : AdsFlowApplication() {

    private val premiumPrefs by lazy {
        getSharedPreferences("premium", MODE_PRIVATE)
    }

    /** Trả về true để tắt toàn bộ quảng cáo. */
    override fun defaultAdSuppressor(): (() -> Boolean)? = {
        premiumPrefs.getBoolean("is_no_ads", false)
    }

    // Bật/tắt ngay khi giao dịch hoàn tất
    fun setNoAds(enabled: Boolean) {
        premiumPrefs.edit().putBoolean("is_no_ads", enabled).apply()
    }
}

Gọi từ nơi xác nhận giao dịch thành công:

PurchaseManager.kt 
fun onPurchaseSuccess() {
    (applicationContext as MyApplication).setNoAds(true)
    // Không cần restart — các màn hình sau sẽ bỏ qua quảng cáo
}

fun onSubscriptionExpired() {
    (applicationContext as MyApplication).setNoAds(false)
}

Bước 9

Các loại quảng cáo từ MainActivity trở đi (Chuẩn hóa 5 Manager)

Từ MainActivity trở đi, app quản lý việc nạp và hiển thị quảng cáo qua 5 Manager chuyên biệt: AdNativeManager, AdBannerManager, AdInterManager, AdOpenManager, AdRewardManager. Tất cả 5 Manager đều kế thừa từ kiến trúc thống nhất BaseAdPlacement và cung cấp đúng 4 hàm tường minh giúp tầng App dễ nhớ, dễ dùng và nhất quán 100%.

💎 4 Hàm chuẩn hóa duy nhất trên cả 5 Manager

App developer chỉ cần nhớ 4 phương thức này khi gọi bất kỳ loại quảng cáo nào:

  • loadOnly(...): Preload quảng cáo vào bộ nhớ đệm (Placement) bằng 1 Ad Unit ID, sẵn sàng show sau với độ trễ bằng 0.
  • loadAndShow(...): Tải về và tự động hiển thị ngay khi nạp xong bằng 1 Ad Unit ID.
  • loadOnlyList(...): Preload theo danh sách Ad Unit ID dự phòng (Cascade fallback).
  • loadAndShowListId(...): Tải và hiển thị ngay theo danh sách Ad Unit ID dự phòng.
  • show(...): Hiển thị một Placement đã tải (hoặc dùng các alias trực quan: showNative, showBanner, showInter, showReward).

🚀 Điểm ưu việt của kiến trúc BaseAdPlacement (Production-Ready)

  • Tối ưu Show Rate (Pending Show): Nếu gọi show() khi quảng cáo vẫn đang tải (LOADING), Placement sẽ ghi nhớ cờ chờ và tự động hiển thị ngay lập tức khi quảng cáo nạp xong (miễn là Lifecycle đang ở trạng thái STARTED hoặc RESUMED). Không bao giờ bị miss impression!
  • Chống Memory Leak 100%: Quản lý vòng đời qua DefaultLifecycleObserver, tự động unbind và cleanup tài nguyên khi Activity/Fragment bị onDestroy. Sử dụng WeakReference cho Activity và ViewGroup.
  • Không dùng Reflection: Truy cập trực tiếp Producer strongly-typed, loại bỏ hoàn toàn mã phản chiếu (Java Reflection), tăng tốc độ thực thi và loại bỏ crash ẩn.
  • An toàn tuyệt đối (Fail-Safe): Nếu cấu hình Remote Config tắt, key trống hoặc user là VIP/Suppressed, Manager tự động dọn sạch giao diện (GONE container) và kích hoạt callback tiếp tục (onNextAction / onAdFailed) để app không bao giờ bị đơ luồng.

Danh mục 5 loại quảng cáo & Vị trí áp dụng

Loại Quảng Cáo Đặc Điểm & Trải Nghiệm Vị Trí Xuất Hiện Tiêu Chuẩn Key Test Trong Demo
1. Banner Ad Dải chữ nhật dẹt cố định ở chân hoặc đầu màn hình. Không ngắt quãng thao tác của người dùng. Dashboard, Màn hình danh sách (List), Màn chi tiết (Detail) banner_all
2. Native Ad Quảng cáo tùy biến giao diện hòa nhập mượt mà vào phong cách app (chứa Icon, Headline, Body, Button CTA). Language Start, Intro Onboarding, Danh sách tin tức (Feed) native_collapse_custom
3. Interstitial Ad Quảng cáo toàn màn hình xuất hiện ngắt quãng giữa các luồng tác vụ. Có cơ chế cooldown / frequency capping chống spam. Sau khi hoàn thành tính năng, Chuyển tab chức năng, Bấm nút Back/Next inter_home
4. Rewarded Video Video toàn màn hình người dùng chủ động bấm xem để nhận phần thưởng (không thể bỏ qua nếu muốn nhận quà). Mở khóa tính năng VIP tạm thời, Nhận Coin / Lượt dùng miễn phí reward_home
5. App Open Ad Quảng cáo toàn màn hình khi người dùng mở ứng dụng hoặc quay lại từ chạy ngầm (Background). Được bảo vệ bởi AppOpenSuppressor. Màn Splash (khởi động app), Màn Welcome Back (quay lại app) app_open_wcb

Ý nghĩa 3 chế độ kiểm thử (Nút bấm)

  • ⚡ Nút [Preload] (Load Only): Gọi phương thức nạp trước quảng cáo vào bộ nhớ đệm (Placement) chạy ngầm. Trạng thái chuyển sang PRELOADED (READY). Dùng khi muốn tối ưu trải nghiệm (ví dụ: nạp ở Splash để sang Intro hiển thị ngay tức thì).
  • 👁️ Nút [Show]: Kích hoạt hiển thị quảng cáo từ Placement đã nạp sẵn trong bộ nhớ đệm. Nếu chưa bấm Preload, hệ thống sẽ cảnh báo Toast yêu cầu nạp trước.
  • 🚀 Nút [Load & Show]: Gộp 2 bước: Vừa gửi yêu cầu tải về, vừa tự động bung hiển thị ngay khi nạp thành công. Thích hợp cho các màn hình không có thời gian nạp ngầm trước.

Bước 10

Cấu hình Remote Config chuẩn

Toàn bộ quảng cáo và luồng điều hướng được điều khiển tập trung từ Firebase Remote Config — có thể tắt/bật, đổi ad unit ID, đổi tần suất và thay layout mà không cần phát hành bản app mới. Thư viện tự động fetch và cache ngay khi vào Splash.

10.1. Cơ chế hoạt động & Nguyên tắc mapping

Khi vào SplashActivity, thư viện gọi IConfigRepository.getConfigObject<T>(key). Dưới nền, thư viện dùng Gson để deserialize chuỗi JSON từ Remote Config thành các Data Class strongly-typed: NativeModel, InterModel, BannerModel, AppOpenModel, RewardModel, ScreenLanguageStart, ScreenSplashModel, ScreenWelcomeBackModel, AdConfigModel.

🐛 Cảnh báo quan trọng về KeyName và Schema JSON

Nếu Remote Config bị sai chính tả tên key hoặc chuỗi JSON bị sai kiểu dữ liệu / cú pháp không hợp lệ, Gson sẽ trả về null hoặc đối tượng mặc định với is_show = false và danh sách ID rỗng. Hệ quả: Quảng cáo sẽ không tải và không hiển thị mà không sinh lỗi crash, gây thất thoát doanh thu rất khó debug!

10.2. Cơ chế Fallback Defaults khi mất mạng (Offline-First cho Thư viện)

Khi ads_flow được đóng gói thành thư viện độc lập (.aar), tầng app truyền file cấu hình mặc định (fallback) để khi người dùng mở app không có mạng hoặc Firebase fetch thất bại, toàn bộ quảng cáo vẫn hiển thị mượt mà từ bộ defaults. Thư viện áp dụng 3 lớp bảo vệ tự động (3-Layer Fallback):

Thứ tựLớp bảo vệCơ chế hoạt độngƯu tiên
Lớp 1 Khai báo tường minh qua AdsFlowConfig App truyền remoteConfigDefaultsRes = R.xml.remote_config_defaults trong MyApplication.configureFlow(). Cao nhất (Khuyên dùng)
Lớp 2 Tự động phát hiện (Auto-detection Zero-config) Nếu dev quên truyền ở Lớp 1, thư viện tự động dò tìm file res/xml/remote_config_defaults.xml trong package của App qua getIdentifier(). Tự động nhận
Lớp 3 Built-in Defaults trong ads_flow Thư viện điền sẵn bộ JSON mẫu và Test Ad Units chuẩn trong file XML của thư viện, đảm bảo không bao giờ bị null config. Dự phòng cuối cùng
MyApplication.kt — Truyền Remote Config Defaults từ tầng App kotlin 
class MyApplication : AdsFlowApplication() {

    override fun configureFlow(): AdsFlowConfig = AdsFlowConfig(
        // ✅ 1. Truyền file XML defaults của tầng app (làm fallback khi fetch remote lỗi):
        remoteConfigDefaultsRes = R.xml.remote_config_defaults,

        activityMap = mapOf(
            FlowTarget.MAIN to MainActivity::class.java,
            FlowTarget.WELCOME_BACK to WelcomeBackActivity::class.java
        ),
        isOnboardingOnce = false,
        // ... UI configs
    )

    // Hoặc cách 2: override hook riêng trong AdsFlowApplication
    override fun remoteConfigDefaultsRes(): Int? = R.xml.remote_config_defaults
}

Các lỗi thường gặp khi tích hợp, cùng cách chẩn đoán và khắc phục.

12.1 · Lỗi 401 Unauthorized khi tải dependency

Kho GitHub Packages từ chối truy cập do thiếu hoặc sai thông tin xác thực.

Cách sửa:

  • Kiểm tra gpr.user và gpr.key đã khai báo đúng trong ~/.gradle/gradle.properties.
  • PAT cần quyền read:packages.
  • Nếu dùng tài khoản org, user phải có quyền truy cập package.

Xác nhận package tồn tại:

https://maven.pkg.github.com/IG-NOVA-TEAM/INV_Lib_Ads_Default/com/ignova/ads-flow-normal/

12.2 · WelcomeBack không hiện dù đã khai báo lifecycle callback

Đây là lỗi phổ biến nhất. Kiểm tra theo thứ tự, dừng ở điều kiện đầu tiên không thỏa:

  1. AdCommon.isShowingAd có đang kẹt true không? Đây là nguyên nhân hay gặp nhất. Biến này được bật ở đầu mỗi màn flow và chỉ được tắt ở một số nơi — nếu một activity bật mà quên tắt, mọi lần resume sau đó đều bị chặn.
  2. Đã override excludedFromWelcomeBack() chưa, và danh sách có chứa nhầm MainActivity không?
  3. Đã map FlowTarget.WELCOME_BACK trong activityMap chưa?
  4. defaultAdSuppressor() có đang trả về true không?
  5. App có còn sống tới khi người dùng quay lại không, hay đã bị hệ thống kill? Khi app bị kill và mở lại, đây là lần khởi động mới — chỉ hiện WelcomeBack khi resume từ background.

Để bật/tắt thủ công khi debug:

AdCommon.isShowResume = true

12.3 · Không thấy quảng cáo nào hiện lên

Sau khi loại trừ lỗi WelcomeBack, kiểm tra theo thứ tự:

  1. Key có tồn tại trên Remote Config chưa, và đúng tên chưa? Key sai chính xác sẽ bị coi là không tồn tại.
  2. Trường is_show có đang là true không?
  3. defaultAdSuppressor() có vô tình trả về true không?
  4. Interstitial có bị chặn bởi interval_between_interstitial không? Mặc định là 20 giây giữa hai lần.
  5. Đã truyền đúng viewLifecycleOwner trong Fragment chưa?

Xem logcat để biết lý do cụ thể — mỗi lần bị bỏ qua đều có log riêng:

adb logcat | grep -E "_null|_suppressed|_ctx_invalid|_pro_null"

12.4 · Build fail: "requires a placeholder substitution but no value for …"

Manifest merger không tìm thấy giá trị cho một placeholder mà thư viện yêu cầu. Thông báo đầy đủ trông như:

Attribute meta-data#com.google.android.gms.ads.APPLICATION_ID@value at AndroidManifest.xml requires a placeholder substitution but no value for <admobAppId> is provided.

Cách sửa: khai báo placeholder tương ứng trong defaultConfig của module app. Xem mục 1.4 để biết chính xác cần những giá trị nào.

12.5 · Quảng cáo không hiện ra dù App ID đã đúng

Bạn đang dùng AdMob test App ID: ca-app-pub-3940256099942544~3347511713. Test ID chỉ hiện test ads, quảng cáo thật của bạn sẽ không bao giờ xuất hiện.

Cách sửa: thay bằng App ID thật lấy từ AdMob Console trước khi phát hành.

Kiểm tra nhanh: mở app/build/intermediates/merged_manifest/<buildType>/…/AndroidManifest.xml, tìm com.google.android.gms.ads.APPLICATION_ID — nếu giá trị kết thúc bằng ~3347511713 thì bạn vẫn đang dùng test ID.

Cách tách ID theo build type ở mục 1.4.

12.6 · App bị mở 2 lần, hoặc hộp thoại "Open with" mỗi lần mở app

Bạn đã đặt intent-filter MAIN/LAUNCHER trên cả SplashActivity và MainActivity. Chỉ một activity được mang LAUNCHER.

Cách sửa: bỏ intent-filter khỏi MainActivity, giữ lại trên SplashActivity của thư viện (như ví dụ ở mục 2.1).

Nếu bạn không muốn dùng flow onboarding của thư viện thì đặt LAUNCHER trên MainActivity và bỏ khai báo lại SplashActivity.

12.7 · Luồng bị kẹt sau khi hiện interstitial

Bạn đặt logic chuyển màn ngoài callback. Khi quảng cáo tải thất bại, onNextAction vẫn được gọi — nhưng code của bạn đã chuyển màn trước đó một lần, gây ra chuyển màn đôi hoặc kẹt luồng.

Cách sửa: đặt toàn bộ logic chuyển màn vào trong onNextAction. Chi tiết ở mục 9.3.

12.8 · Quảng cáo hiện sai chỗ hoặc hiện ở màn không mong muốn

Container quảng cáo nằm sai vị trí trong layout, hoặc key đang trỏ tới vị trí không dành cho màn hình đó.

Cách sửa:

  • Đảm bảo mỗi container có layout_height="wrap_content" và nằm đúng vị trí.
  • Kiểm tra key trên Remote Config có đúng vị trí bạn cần không.
  • Nếu container bị giữ chỗ trống khi không có quảng cáo, thư viện đã tự ẩn và xoá view con — hãy kiểm tra lại khai báo ban đầu.
12.9 · App bị treo ở Splash

Màn Splash có timeout cứng là 90 giây; timeout fetch Remote Config là 15 giây. Sau thời gian này luồng vẫn phải đi tiếp.

Kiểm tra:

  • Mất mạng lúc mở app → app chuyển sang NoInternetActivity, không phải treo.
  • Thiếu khai báo FlowTarget.MAIN trong activityMap → không biết đi đâu sau flow. Xem bước 3.
